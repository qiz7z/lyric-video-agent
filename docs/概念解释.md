## 1. 音频：ffmpeg 解码为立体声 wav

**一句话**：把压缩歌曲文件变成电脑能直接做数学运算的原始声音数据。

**拆解**
- **ffmpeg**：一个开源的音视频处理工具（命令行程序），专门干「读取各种格式、转换格式」这种体力活。在我们流水线里它就是负责格式转换的。
- **解码**：你给的歌通常是 `.mp3` / `.m4a` / `.flac` 这种**压缩格式**——为了体积小，里面存的是「差值/算法」而不是完整声音。解码 = 把这些压缩数据**还原成连续的波形数字**（每秒 44100 个采样点，每个点是一个振幅数值）。还原之后，程序才能对数字做运算，比如「找出人声从哪一秒开始响」。
- **立体声 wav**：
  - **wav** 是一种「不压缩、原样存波形」的格式，相当于照片里的 RAW/BMP——体积大，但数据全在，机器最好处理。后面的 demucs 抽人声、算能量定位起唱点，全都要在这上面做。
  - **立体声** = 左右两个声道（左耳/右耳各一份数据）。人声分离模型 demucs 吃立体声比单声道准，所以特意保留双声道，而不是合并成单声道。

**类比**
> mp3 就像压缩过的 JPEG 图片——方便发微信、体积小，但你没法直接拿它做像素级分析。
> wav 就像没压缩的 BMP/RAW——体积大，但每一个采样点（像素）都在。
> ffmpeg 解码 = 把 JPEG 还原成像素矩阵，好让后续程序去「数像素」。

**在项目里的位置**
流水线第 1 框。你 `@` 一首歌（比如 `再见 - 张震岳.mp3`），第一个动作就是 ffmpeg 把它转成一份 `xxx.wav`。这份 wav 不直接给你看，它是**给后面机器步骤当原材料的**——紧接着第 3 框 demucs 就用它抽人声，第 4 框对齐就用它算「人声哪一秒起、哪句和哪句之间安静」来切字幕。

## 2. 主流程图里各箭头 / 连线是什么意思

> **节点 vs 连线**：前面「第 N 框」讲的是一个个**节点**（一个步骤）；这里讲节点之间的**箭头**（数据/控制怎么流）。
> 看图套路先记住两条：
> - **实线 `-->`** = 主流程、必走的硬依赖；**虚线 `-.->`** = 软关系（可选参考 / 并行 / 上下文喂入），边上文字是「这股数据是什么」。
> - **菱形 `{}`** = 判断/分支（里面写判断条件，分出的几条线标「走哪条」）；**圆角/矩形框** = 一个处理步骤。

**从根输入分出的两条主干**
- `源音频文件 --> 1. 音频 ffmpeg 解码`：**实线**。你给的文件先被解码成 wav，去走视频生成主链。
- `源音频文件 --> META（提取 歌名/歌手）`：**实线**。同一文件顺便解析出歌名+歌手（从文件名或音频内嵌 ID3 标签）。这股元数据**不进视频主链**，专门供给下面两个地方。

**META（歌名歌手）分到的两条虚线**
- `META -.->|标题歌手| Planner`：**虚线，标签「标题歌手」** = 歌名+歌手作为**上下文喂给 Planner**。Planner 要决定主题/意象/段数，必须先知道这是哪首歌（详见待补列表「Planner」一节）。不给它歌名歌手，它就只能套通用模板，主题容易和歌不对味（详见第 4 节 Planner）。
- `META -.->|并行生成| 封面 Agent`：**虚线，标签「并行生成」** = 封面 Agent 也吃歌名歌手，而且它和视频生成**同时跑、互不耽误**。这是封面能「并行」的关键（详见待补列表「封面 Agent 并行支线」一节）。

**Planner 与封面 Agent 之间的一条细虚线**
- `Planner -.->|主题可选| 封面 Agent`：**虚线，标签「主题可选」** = Planner 规划出的主题，封面 Agent **可以**拿来参考，但**不是必须**。封面 Agent 主要靠联网调研（搜这首歌的意境/常见封面风格）生图，只有调研没产出时才 fallback 用 Planner 的主题。所以是「可选参考」，不是硬依赖。

**封面 Agent 汇合回主链**
- `封面 Agent -.->|汇合报告| 运行报告`：**虚线，标签「汇合报告」** = 封面跑完后，把封面产物/决策汇合进最后一步「运行报告」，和视频主链的最终产物一起写进报告。

**几个固定套路（以后看图直接套）**
- 紫色节点之间的 `-.->|LLM 决策点|`：**虚线，标签「LLM 决策点」** = 这一步是「让大模型拍板」的地方（Planner 拍板主题、修复循环让模型自修、视觉质检让模型判人物/变形）。
- 橙色节点 `6. 人工听感闸门`：`否 → 终止重跑`、`是 → 继续` = 整条链路**唯一需要你本人点头**的地方，模型不能替你决定「字幕对不对味」。
- 菱形 `{}`：`ratio = 段数/行数`（三路由）、`质量门槛`（修好没）、`人物/变形/离题`（生片合不合格）= 判断条件，分出的线标「走哪条分支」。

## 3. 歌词：内嵌 LRC → LRCLib 兜底

**一句话**：拿到这首歌「带时间轴的歌词」——优先从文件内部读，读不到再去网上歌词库抓。

**拆解**
- **LRC**：歌词的标准格式，每行前面带「这句从哪一秒开始唱」的时间戳，例如：
  ```
  [00:12.34]说再见 别说永远
  [00:18.50]说爱我 别说抱歉
  ```
  那个 `[00:12.34]` 就是时间轴——字幕要对准人声，全靠它。没有时间轴，字幕就不知道该在哪一秒冒出来。
- **内嵌**：很多 mp3 文件内部自带一段歌词（藏在 ID3 标签的 `USLT` 字段里），相当于文件自己口袋里揣了歌词。这种情况最理想：直接从文件里掏出来，**零网络、零校准**，时间轴和这首音频 100% 对得上。
- **LRCLib**：一个**免费的在线歌词数据库**（网站 + API），存了海量歌曲的 LRC。
- **兜底**：安全网 / 备胎。如果文件里没内嵌歌词（大多数歌都没有），就用「歌名 + 歌手」去 LRCLib 搜，把 LRC 下载回来。代价：偶尔抓到的是别的版本的歌词/时间轴，可能和你这首差几秒——所以后面才有「第 4 框对齐」来修偏移（见待补列表「对齐 / 起唱点」）。

**类比**
> 内嵌 LRC 像「书里夹着的现成书签」——翻开就有，位置准。
> LRCLib 兜底像「图书馆没夹书签，去问管理员要一份目录」——能拿到，但版本偶尔不对，得自己核对一下页码。

**在项目里的位置**
流水线第 2 框（在「音频解码」之后、「规划」之前）。它产出的歌词会送两处：
- **Planner**：歌词内容决定主题/意象（伤感歌词 → 萧瑟主题，欢快歌词 → 明亮主题）。
- **第 4 框对齐**：用 LRC 时间轴把字幕一句句贴到人声上，实现「唱一句出一句、唱完即清」。

**具体例子**
- 「再见 - 张震岳.mp3」文件里嵌了歌词 → 直接读 `USLT`，秒出且和音频严丝合缝。
- 没嵌 → 拿「再见 / 张震岳」去 LRCLib 搜，拉一份 LRC；万一时间轴偏了，后面对齐步骤自动校正。

## 4. Planner（规划）：主题 / 意象流 / 段数

**一句话**：**规划**这一步由 **Planner**（紫色 `D[Planner 规划]` 节点）这个 Agent 来执行，产出"拍摄大纲"的三要素：主题、意象流、段数。

> **图里现在合并成一个 `D[Planner 规划]` 紫框**：把"出主题/意象/段数"和"Planner 代码硬校验"写在一起——框里同时标了三要素和"代码硬校验段数与人物词"。之前图里拆成 `D[规划]` + `D1[Planner]` 两个框、用 `LLM 决策点` 虚线连，是为了强调"规划由 LLM 拍板、代码把关"；现在应你的要求合并成一框，护栏含义直接写在框里（"代码硬校验"）。核心是：**规划这步由 Planner Agent 执行，且不是纯 LLM 自由发挥，有代码校验当护栏**——这是项目亮点。

**拆解（Planner 输出什么）**
- **`prompts` = 各段视频生成提示词列表 —— 这是 Planner 最核心的产出**：一个长度 = 段数的**英文提示词数组**，每段一条，直接喂给 Agnes 生那一段视频。它**不是抽象"意象流"，而是已经落地的成品 prompt**：每条用英文、含 1-2 个记忆点意象、默认纯风景、禁人物，还固定带 `negative_prompt` 排除人物与文字水印。`orchestrator._stage_generate` 里就是 `for i, prompt in enumerate(plan["prompts"], 1): gen.generate(prompt, ...)` 直接用。所以**你问的"各段视频生成提示词的地方"，就是这里**——Planner 一次性把每段要生什么景的英文指令全写出来。
  - 例子「再见」13 段的 `prompts[0]` 可能 ≈ `"dusk at an empty train station, lonely bench, cold blue tone, cinematic, no people"`（车站暮色、孤椅、冷蓝调、无人物）。
  - 注意：QC 阶段若某段画面不合格，verifier 会产出 `revised_prompt`（改写后的英文风景 prompt）去重生成，所以**源头在 Planner，但最终用的 prompt 可能是修复循环改过的版本**。
- **主题（theme）= 整体情绪基调**：一句话概括这首歌唱什么情绪、该用什么视觉调性。它决定 `prompts` 里所有画面的"滤镜感"（冷/暖、亮/暗）。
  - 例子：「再见 - 张震岳」离别伤感 → 主题 **「萧瑟、黄昏、独行」**；「乡间小路」轻快童谣 → 主题 **「明亮、田园、暖色」**。
- **意象流（imagery flow）= `prompts` 的中文前身 / 中间构思**：把主题落成**一串具体风景画面**的设想（如 `车站暮色 → 落叶街角 → 远去的铁轨 …`），Planner 再把它逐条翻译成上面的英文 `prompts`。因为项目默认纯风景、不要人物（避免 AI 把人画变形），意象流里全是景。简单记：**主题 = 调性；意象流 = 这一路想放哪些景（中文构思）；prompts = 这些景翻译成的英文生片指令（最终落地）**。
- **段数（`n_clips`）= 整首歌切成几段视频**：一首 3 分钟的歌不能一段 AI 视频搞定（太长易崩也贵），Planner 按**音频时长**切成 N 段，每段约 15 秒，每段单独用 Agnes 生成。段数由时长公式算：`N×15.06 - (N-1)×0.3 ≈ 覆盖时长`。
  - 13 段 ≈ 192 秒、18 段 ≈ 266 秒、19 段 ≈ 281 秒、21 段 ≈ 310 秒；长歌（>4 分钟）一般 18 段以上。
  - 段数直接决定 `prompts` 列表长度、调 Agnes 多少次、花多少时间（25–40 分钟/首）。

**Planner 吃哪三个输入**（回看第 2 节那几条虚线就懂了）
- **歌名歌手**（META 虚线 `|标题歌手|` 喂来的）→ 知道"这是哪首歌"，定主题/意象才对味。
- **歌词内容**（第 2 框来的）→ 伤感歌词 → 萧瑟意象，欢快歌词 → 明亮意象。
- **音频时长**（解码后能量分析得到）→ 决定切几段。

**类比**
> Planner 像「AI 导演拿到一首歌，先写出分镜脚本」：情绪基调（主题）+ 一路放哪些景（意象流）+ 拍几场（段数）。后面所有步骤（生片、字幕、合成）都是照这个脚本执行。

**代码位置**
`orchestrator.py` 里调 Planner 时，把 `title` / `artist`（从文件名解析）、`lyrics`（第 2 框）、`duration`（解码得到）作为参数传进去，Planner 返回 `{"theme":..., "n_clips": N, "prompts": ["英文 prompt×N"], "font":..., "trim_intro_seconds":...}`。其中 **`prompts` 就是你问的"各段视频生成提示词"**——`_stage_generate` 直接用 `plan["prompts"]` 逐段调 Agnes。图上的 `D[Planner 规划]` 紫框，就是这次调用的可视化。

## 5. 对齐：demucs 人声分离 → onset 切段

**一句话**：对齐 = 让**字幕（每句歌词）的起止时间，精确贴在人声真实演唱的那一秒**——也就是你说的"视频字幕与音频声音对齐"。你的直觉对，但图里"切段"的"段"容易和 Planner 的"段数"搞混，下面专门厘清。

**拆解（这框干了什么）**
- **demucs 人声分离**：用 demucs 模型把歌曲里的"人声"单独抽出来，去掉伴奏、鼓点、贝斯，得到一条干净的人声波形（`vocals.wav`）。为什么去伴奏？伴奏的鼓点/镲会制造能量假峰，直接拿全曲算"哪秒在唱"会被鼓点带偏；抽干净人声后，算它的能量（RMS）才准。
- **onset 切段**：`onset` = "起唱点"（人声从哪秒开始响）。算法用自适应阈值在干净人声的能量曲线上切出"人声正在演唱的段落"（`[[start,end],...]`），这些段就是字幕对齐的**骨架**——标出每一句歌词应该落在哪段时间窗里。
- **三路路由**（按 `ratio = 人声段数 ÷ 歌词行数` 选映射策略）：
  - `ratio ≈ 1`（段≈行）→ `sequential`：DP 单调对齐，以 onset 段为骨架、歌词按出现顺序装填（最准）。
  - `ratio >> 1`（段远多于行，如 DJ/重复副歌）→ `lrc_primary`：信 LRC 时间轴，onset 只在 ±1.2s 内微调。
  - `ratio < 1`（段少于行）→ `interp`：LRC 直接打底，建议人工锚点校准。
- **事件化（最终产出）**：把每句歌词变成一条字幕事件 `events = [{start, end, text}]`，其中 `start = 人声起唱点`、`end = 下一句起点`（零空隙零重叠），实现"唱一句出一句、唱完即清"。

**⚠️ 两个"段"不是一回事（图里最容易看懵）**
- **Planner 的"段数 N"（第 4 节）** = 切成几段**视频**：每段约 15 秒，喂 Agnes 生一段风景视频。这是"物理切片"，N 一般 13~21。
- **对齐的"onset 切段"（本框）** = 切出**人声演唱的小段**：细粒度（一句词可能就 2~4 秒），用来**定位字幕的逐句时间点**。这不是切视频。
- 关系：字幕时间轴（align 产出）最终会被烧录到对应的视频段里。所以"段"在图里出现两次，但含义不同——视频段是"拍几场"，人声段是"歌词卡点对哪句"。

**类比**
> demucs 抽人声 = 先把伴奏静音、只留歌手清唱；onset 切段 = 听清歌手"每一句从哪秒开口"；对齐 = 把字幕条按这个开口时间贴上去，歌手张嘴字幕就亮、唱完就灭。

**代码位置**
`tools/align.py` 的 `align(vocals_envelope, lyrics, duration)` 返回 `(events, report)`：`events` 就是字幕时间轴（`_stage_align` 把它存成 `events.json`），`report` 是质量报告（route/ratio/delta 等，供人工或修复循环审阅）。图上的 `E[4. 对齐]` 框，就是这次调用。

## 6. ratio = 段数 / 行数（对齐三分支的路由判断）

**一句话**：`ratio = 人声小段数 ÷ 歌词行数`，是个**数量配比**。对齐算法靠它判断"切片粒度"和"歌词行数"谁多谁少，从而选三条不同的贴字幕路线（第 5 节的菱形判断）。

**拆解（分子和分母分别是什么）**
- **分子"段数"** = 第 5 节里 demucs 切出来的**人声小段**数量（onset 段数，比如一首歌被切成 30 个"正在演唱的段落"）。⚠️ 注意它**不是 Planner 的视频段数 N**（那是切几段视频，一般 13~21）——`ratio` 里用的是**人声小段数**，比视频段数细得多（可能几十个）。
- **分母"行数"** = 歌词总共多少行（LRC 里有几行词）。
- **ratio = 段数 ÷ 行数**，衡量"人声小段"和"歌词行"是不是一样多。

**为什么需要这个比值**
对齐的本质是"把第 i 行歌词，安排到第 i 段人声的时间窗里"。但人声小段数和歌词行数**经常不相等**（一首歌唱法和词本就不一一对应，或 DJ 重混重复副歌）。硬套一种贴法会贴错（字幕提前/滞后/重复）。`ratio` 把数量关系分三类，每类有最稳的贴法。

**三分支（代码阈值 `align.py:126-132`）**
| ratio | 路由 | 适用情况 | 怎么贴字幕 |
|---|---|---|---|
| `≈ 1`（段数≥行数 且 ≤2.0） | `sequential` | 一行配一段，最理想 | DP 单调对齐：以 onset 段为骨架，歌词按出现顺序装填（最准） |
| `> 2.0` | `lrc_primary` | 段远多于行（DJ/重复副歌） | 信 LRC 时间轴，onset 只在 ±1.2s 内微调（防跨副歌吸附暴偏 3~9s） |
| `< 1.0` | `interp` | 段少于行（词太多格太少） | LRC 直接打底，近处有 onset 就吸附，并提示"建议人工锚点校准" |

**具体例子（更好懂）**
- **sequential（ratio≈1）**：《再见》歌词 30 行、人声被切成 30 个小段 → `30÷30 = 1.0` → 一行配一段，干净。
- **lrc_primary（ratio>2）**：某 DJ 重混版，副歌"爱你爱你"被重复唱，歌词还是 30 行，但人声小段被切成 75 段 → `75÷30 = 2.5` → 这时**不能信人声段数**（会跨副歌把字幕吸附乱，暴偏 3~9 秒），改信 LRC 原时间轴、onset 只微调。
- **interp（ratio<1）**：长叙事歌歌词 50 行，但人声小段只切出 11 个（一段塞不下这么多词）→ `11÷50 = 0.22` → LRC 打底、就近吸附，并建议人工校准。

**代码位置**
`tools/align.py` 的 `align()` 里 `ratio = len(segs) / len(lyrics)`（segs=人声小段，lyrics=歌词行），`if len(segs) >= len(lyrics) and ratio <= 2.0: sequential / elif ratio > 2.0: lrc_primary / else: interp`，最终 `report["route"]` 记下走了哪条。图上 `F{ratio = 段数/行数}` 菱形分出的三条边，就是这个判断。

### 6.1 ratio > 2.0 触发 `lrc_primary`：具体怎么贴字幕

**一句话**：ratio>2 时，对齐算法**不再迷信"人声段数"，改以 LRC 时间轴为主基准**来排每句字幕的起点；人声 onset 只当"±1.2 秒微调器"，不跨段吸附。

**为什么 ratio>2 必须换打法（对比 sequential）**
- `sequential`（ratio≈1）是以 onset 段为骨架，把歌词按出现顺序装填到各段——前提是"段和行一一对应"。
- 一旦 ratio>2，说明**人声小段比歌词行多一倍还多**。最常见是 DJ 重混 / 重复副歌：歌词就 30 行，但副歌"爱你爱你"反复唱，demucs 把每次重复都切成独立 onset 段 → 75 段。`75÷30 = 2.5`。
- 这时若还走 sequential，会把同一行"爱你"在 75 个碎段里到处派发、跨副歌吸附到第二次重复去，字幕**提前/滞后 3~9 秒**（实测过的漂移量级）。所以"段数"已不可信 → 改信 **LRC 原时间轴**（平台/人工标好的，副歌重复也只标一次时刻），onset 只吸收 1.2s 内的小误差。

**`lrc_primary` 的逐行贴法（`tools/align.py:_align_lrc_primary`，252-267 行）**
对每一行歌词：
1. 看它 LRC 时间 `lrc_t` 附近 **±1.2 秒窗口内**（`LRC_CORR = 1.2`）有没有 onset 起点；
2. **有、且保持单调**（该 onset 必须晚于上一句起点，不能倒退）→ 吸附过去（`ss = 那个 onset`，标记 `src="onset"`），吸收这 1.2s 内的小漂移；
3. **附近没有 onset** → 直接用 LRC 时间（`ss = lrc_t`，标记 `src="lrc"`），不硬凑、不跨段。
4. 关键约束：**吸附窗口只有 ±1.2 秒**，所以绝不会把"爱你"这句吸到副歌第二次重复（那在几秒甚至几十秒外）去。

**具体例子**
《某 DJ 重混版》：歌词 30 行、人声小段 75 段 → `ratio = 2.5 > 2.0` → 走 `lrc_primary`。
- 副歌"爱你"在 LRC 里标了 90s、120s、150s（重复三次，各一次时刻）；
- 每行按 LRC 时刻排起点，onset 只在 ±1.2s 内微调（比如 90.0s 附近真有起唱 90.3s → 吸附成 90.3s）；
- 结果：字幕跟着 LRC 走，**不会被 75 个碎段带偏**，句与句零空隙零重叠。

**边界提醒（代码 `:127-132` 三分支的完整覆盖）**
- `段数 ≥ 行数 且 ratio ≤ 2.0` → `sequential`（段不太碎，还能当骨架）；
- `ratio > 2.0` → `lrc_primary`（段太碎，信 LRC）；
- `段数 < 行数`（即 `ratio < 1.0`）→ `interp`（段不够，LRC 打底 + 就近吸附，建议人工校准）。
- 注意 ratio 在 1.0~2.0 之间仍走 sequential；**只有越过 2.0 这道线才翻到 lrc_primary**。

## 7. 修复循环 + 质量门槛（delta_max ≤ 3s 且不劣化）

**一句话**：对齐（第 5/6 节）产出的字幕时间轴可能不够准，需要一个**会自己改参数、再验收**的环节来修正它。这个环节就是紫色 `J[修复循环]`，而你要问的那个菱形 `J1{质量门槛 delta_max ≤ 3s 且不劣化}` 是它每改一次之后的**验收关卡**——不达标就作废、自动回退重来（最多 3 轮）。

**先说 delta 是什么（门槛的核心词）**
- `delta` = 某一句字幕的实际显示时间，和**人声真实起唱点**差了几秒（对齐偏差，单位秒）。
- `delta_abs_mean` = 所有句子偏差的**平均**值；`delta_abs_max` = 所有句子里**偏差最大的那句**。
- 对齐越准，delta 越小（理想是 0）。

**修复循环怎么跑（`repair.py`）**
1. LLM 通过 **function calling**（函数调用）在工具箱里自主决策：`re_align`（重对齐）、`set_trim`（裁前奏）、`accept`（接受）。
2. 每调一次工具，就得到一个候选字幕时间轴 + 它的质量报告 `report`。
3. 把候选送进**质量门槛（J1 菱形）**验收 → 通过就采纳、不通过就 REJECTED 回退到当前最优、进入下一轮（最多 `max_rounds=3` 轮）。

**质量门槛的两个条件（必须都满足才 ACCEPTED，`_gate` 代码 `repair.py:122-130`）**
- **① delta_max ≤ 3s**：候选里"偏差最大那句"也不能超过 3 秒（`DELTA_MAX_OK = 3.0`，`:23`）。即最坏的字幕，和人声对得也不要飘出 3 秒。这是**硬门槛**。
- **② 整体不劣化**：候选的"质量分"必须**优于或等于**当前已采纳的最优结果（`_quality(creport) ≤ _quality(cur_report)`），否则 REJECTED。质量分 `_quality` 是 `(路由等级, -平均偏差)` 的字典序（`:27-30`）：先比走了哪条路由（sequential 最值钱 > lrc_primary > interp），再比平均偏差越小越好。意思是**不能越修越烂**。

**REJECTED 回退（`J1 -->|REJECTED 自动回退| J`）**
任一条不满足 → 这次尝试作废，回到"当前最优结果"继续下一轮（不是从头重来）。3 轮内都没有更优候选 → 自动接受当前最优。所以**质量门槛是一道护栏，保证最终进 `events.json + report.json`（K 框）的字幕，不会比改之前更差**。

**真模型实测的失效模式（这是实习亮点，`runs/梦的光点/repair_real_trajectory.json`）**
用 Agnes 真模型跑《梦的光点》时，LLM 曾**盲目抖动 `set_trim` 参数**（以为调裁前奏能更好），结果某候选 `delta_max = 15.1s`（有一句字幕飘了 15 秒）。幸亏 `delta_max > 3.0` 门槛当场 REJECTED、自动回退——这 15 秒的劣化**没污染成品**。这恰恰证明了"质量门槛"不是摆设：没有它，字幕就会乱飘十几秒。这个"LLM 会乱调参数、必须靠代码硬门槛兜底"的故事，就是你找实习时讲 Agent 可靠性的好素材。

**代码位置**
`agent/repair.py`：`RepairLoop.run()` 跑循环，`_gate()` 是质量门槛（条件① `:126-127`、条件② `:128-130`），`DELTA_MAX_OK = 3.0` 是门槛常量。图上 `J[修复循环]` →（LLM 决策点虚线）→ `J1{质量门槛}` 菱形，分出的 `REJECTED 自动回退` 边回到 J、`通过` 边去 K，就是这段逻辑。

## 8. events.json + report.json（对齐阶段的"双产物"）

**一句话**：对齐（第 5/6/7 节）跑完，落盘成两个 JSON 文件——`events.json` 是**字幕时间轴蓝图**（每句歌词从哪秒亮到哪秒灭），`report.json` 是**对齐质量验收单**（这次对齐排得准不准）。图上 `K[events.json + report.json]` 这个框，就是它俩一起代表对齐阶段（Stage 4）的最终交付。

**拆解（每个文件装什么）**
- **`events.json` = 字幕时间轴**：一个 JSON 数组，每行歌词一条记录：
  ```json
  [
    {"start": 12.34, "end": 18.50, "text": "说再见 别说永远", "src": "onset", "lrc": 12.34, "delta": 0.0},
    {"start": 18.50, "end": 24.10, "text": "说爱我 别说抱歉", "src": "lrc",   "lrc": 18.50, "delta": 0.0}
  ]
  ```
  - `start` / `end`：这句字幕**从哪秒亮、到哪秒灭**（贴在人声真实起唱点 / 下一句起点）。
  - `text`：这句歌词原文（要烧进视频的字）。
  - `src`：这句起点来自哪——`onset`（人声检测到的）/ `lrc`（直接用的 LRC 时间）/ `interp`（插值兜底）。
  - `lrc`：LRC 原标的时间戳，留着对照。
  - `delta`：实际起点与"人声真实起唱点"的偏差秒数（对齐准不准的逐句证据）。
  - 这就是"唱一句出一句、唱完即清"的**数据蓝图**。下游 `gen_ass.py` 读它生成 ASS 字幕文件，再烧进对应的视频段。
- **`report.json` = 质量验收单**：一个 JSON 对象，记录这次对齐的"体检报告"：
  - `route`：走了哪条路由（sequential / lrc_primary / interp，对应第 6 节菱形判断）。
  - `ratio_onset_to_line`：第 6 节的 ratio 值。
  - `n_lyrics` / `n_onsets`：歌词行数 / 人声小段数。
  - `delta_abs_mean` / `delta_abs_max`：平均偏差 / **最大偏差**（秒）——第 7 节质量门槛盯的就是 `delta_max`。
  - `src_counts`：onset / lrc / interp 各占几句（能看出"多少句靠人声检测、多少句靠 LRC 兜底"）。
  - `long_gaps`：相邻句间隙 > 阈值的列表（提示哪几句之间可能空太久）。
  - 这份报告是给**人和修复循环**看的：人工听感闸门（橙色框）审阅它判断字幕对不对味；修复循环用 `delta_max` 当验收关（第 7 节 J1）。

**为什么是"两个文件"（加号的意思）**
- `events.json` 管"**执行**"——机器下一步照它烧字幕；`report.json` 管"**验收**"——人和护栏照它判断是否合格。
- 这正是第 7 节末尾那句"保证最终进 `events.json + report.json` 的字幕不会比改之前更差"的含义：修复循环每改一轮，都用 `report.json` 里的 `delta_max` 验收，通过了才把**新的** `events.json` 落盘，没通过就回退到当前最优——所以"进 K 框的那份"始终是验收过的最优版。

**代码位置**
- `orchestrator.py:_stage_align`（168-196 行）把 `align()` 返回的 `(events, report)` 写成 `work/events.json` 和 `work/report.json`。
- 若这俩文件已存在，重跑会**直接复用**（`if ev_file.exists()`，169-173 行）不再重算——想重新对齐要先删掉它们（对齐重算后代码也会自动作废过期的验证版/成片，199-202 行）。
- 图上 `K[events.json + report.json]` 框 = 对齐阶段（Stage 4）的终点；下游一支去"烧字幕"（`gen_ass.py` 读 events.json），一支去"人工听感闸门"（看 report.json）。

**具体例子**
《再见》对齐完：`events.json` 里 30 条记录排好每句起止；`report.json` 写 `{"route":"sequential","ratio_onset_to_line":1.0,"delta_abs_max":0.3,...}`——说明走最优 sequential、最大偏差才 0.3 秒，质量好，直接进人工闸门。
